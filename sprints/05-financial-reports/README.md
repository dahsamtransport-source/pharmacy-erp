# Sprint 5 — التقارير المالية

هذه الوحدة تنفذ طلب التقارير فوق الكود الفعلي في Sprint 2، على الفرع `sprint5/ympharma-financial-reports` انطلاقًا من `6c9ca69593afa6a100594b449db0eb24aed1c244`. تسميتها Sprint 5 تتبع طلب المالك؛ لا تعني أن وحدات Sprint 3 و4 غير الموجودة أصبحت منجزة.

## التنفيذ

- واجهة `src/FinancialReports.tsx` تحل محل التقرير الأولي داخل تبويب التقارير الموجود؛ لا شاشة معزولة أو بيانات مصطنعة.
- ميزان مراجعة: رمز واسم وتصنيف الحساب، افتتاحي مدين/دائن، حركة مدين/دائن، ختامي مدين/دائن، إجماليات وفحص توازن الأقسام الثلاثة.
- قائمة دخل: الإيرادات، تكلفة المبيعات، مجمل الربح، المصروفات التشغيلية، صافي الربح أو الخسارة. حساب تكلفة المبيعات يأتي من الربط المحاسبي الموجود؛ غيابه أو تصنيفه خطأ يمنع تقريرًا مضللًا.
- فترة بالتاريخ المحاسبي ومركز تكلفة اختياري، مع خيار الحسابات الصفرية. بداية الفترة تستخدم منطقة المنشأة الزمنية حتى عند تغيّر الشهر قبل/بعد UTC.
- فترة العرض والطباعة تأتي من الاستجابة المؤكدة، لا من المدخلات التي عدّلها المستخدم ولم يحدّث التقرير بعدها. الطباعة والتصدير معطلان أثناء التحميل والفشل والتعديل غير المطبق.
- الترويسة تعرض اسم المنشأة الفعلي، العملة، مركز التكلفة، فترة التقرير، عدد القيود ووقت جلب البيانات. لا يوجد اسم شركة أو عملة ثابتة في المكون.
- A4 أفقي لميزان المراجعة وعمودي لقائمة الدخل، وقواعد للطباعة بالأبيض والأسود. اختبار المظهر الفعلي على الطابعة ما زال مطلوبًا.
- CSV مع BOM للعربية، تهريب علامات الاقتباس والتحييد النصي لبدايات صيغ الجداول الحسابية، وحفظ القيم العشرية دون تحويلها إلى Number.
- حالات فارغة وفشل وانقطاع اتصال منفصلة. القاعدة الفارغة لا تعرض رسالة نجاح محاسبي. التوازن العددي لا يثبت اكتمال القيود أو الموافقة الضريبية.

## تصحيح المقطع المقترح

| في المقطع المرسل | ما ينفذه المشروع |
|---|---|
| جداول `chart_of_accounts` و`journal_entries` مفترضة | استخدام `ym.accounts` و`ym.journals` و`ym.journal_lines` الموجودة |
| دالة دخل SECURITY DEFINER لكل authenticated | دوال SECURITY INVOKER مع RLS وفحص دور المالك/المدير/المحاسب |
| تجميع أسطر قد تشمل قيودًا غير مرحّلة | مصدر `ym_api.ledger` المقيد بحالة posted |
| حدود UTC حتى 23:59:59 | تواريخ أعمال DATE شاملة لليوم الأخير، دون إسقاط أجزاء الثانية أو تغيير يوم المنشأة |
| جمع قيم مالية بـJavaScript Number | SQL numeric وقيم نصية وBigInt للفحص والتنسيق |
| قائمة دخل تجمع كل المصروفات دون تفصيل | فصل تكلفة المبيعات عن بقية المصروفات بحسب الربط المعتمد |
| شارة توازن حتى عند فشل الجلب أو عدم وجود سجلات | لا تقرير قابل للطباعة عند الفشل، ولا شارة اكتمال عند الفراغ |
| تاريخ عنوان قابل للتغيير قبل جلب البيانات | عنوان مرتبط بنسخة البيانات التي أعادها الخادم |

عرض PostgreSQL العادي ليس ذاكرة تجميع مسبق ولا وعدًا بسرعة ثابتة؛ الاستعلام يُنفذ عند القراءة. الفهارس الحالية تغطي ربط الحساب والقيود والتاريخ، وأضيف فهرس جزئي لمركز التكلفة والتاريخ في القيود المرحّلة. تجميع الأرصدة يُحسب مرة واحدة داخل استدعاء التقرير. لم يُنفذ اختبار تحميل يثبت أداء آلاف المستخدمين.

FEFO يحدد **التشغيلة المصروفة**. تكلفة البضاعة في المحرك الحالي تعتمد على **المتوسط المرجح المتحرك**، ولا تصبح «تكلفة FEFO» لمجرد استخدام FEFO في الصرف.

## قاعدة البيانات وعقد القراءة

الهجرة الخامسة داخل مسار التقييم، وليست ضمن هجرات الإنتاج:

`sprints/01-database/supabase/migrations/20260920020919_ympharma_financial_statements.sql`

- `ym_api.financial_report_options(p_org)` يعيد مراكز التكلفة المرئية للمستخدم المالي.
- `ym_api.financial_report_v2(p_org,p_from,p_to,p_center,p_include_zero)` يعيد التقرير كله من لقطة القراءة نفسها: بيانات المنشأة والأرصدة والإجماليات وقائمة الدخل.
- `financial_report` القديم والعروض القديمة بقيت متوافقة مع العملاء السابقين؛ الواجهة الجديدة تستخدم v2.
- كل الدوال تقيد التنفيذ وتفحص الدور والعضوية. المخططات الداخلية لا تُعرض للمتصفح. غياب العضوية أو سحبها أو معرف مركز من منشأة أخرى يمنع القراءة.
- يرفض التقرير تواريخ غير صالحة، أو فرقًا يتجاوز 366 يومًا بين التاريخين، أو قيودًا بعملات مختلطة. لا يُخفي العملات المخالفة لتجميل الأرقام.
- الحسابات غير النشطة تحتفظ بتاريخها؛ حسابات التجميع لا تُجمع مرة ثانية. الأرصدة غير العادية والقيود العكسية تحافظ على إشارتها.
- عقود Zod تفحص شكل البيانات والتوازن الحسابي الداخلي والإجماليات وملكية المنشأة والفترة. فشل العقد يمنع عرض استجابة غير متوافقة.

التقارير تتجدد عند فتحها والضغط على «تحديث التقرير». لا يوجد اشتراك دفع حي Realtime أو ادعاء تحديث الخلفية المستمر.

## التشغيل والتقييم

اتبع إعداد مشروع Supabase الاختباري في `sprints/02-frontend/README.md`. على مشروع **تقييم فارغ** طبّق الهجرات الخمس بالترتيب، ثم التهيئة وحسابات الاختبار والقوائم الأساسية. إذا كانت الهجرات الأربع الأولى موجودة في مشروع التقييم، راجع وطبّق الهجرة الجديدة فقط. لا تطبقها تلقائيًا على مشروع إنتاج أو على المخطط القديم الموازي.

```sh
npm ci
npm ci --prefix sprints/01-database --ignore-scripts
npm test
npm run test:db
npm run lint
npm run build
npm run typecheck
npm run dev
```

الربط يستخدم عنوان Supabase ومفتاح publishable العام من إعدادات Sprint 2. لا تحتاج التقارير مفتاح AI أو service_role أو أسرارًا إضافية. افتح «التقارير المالية» بحساب مالك أو مدير أو محاسب. يمكن حفظ PDF من مربع طباعة المتصفح عند اختباره على جهاز فعلي.

## حدود الاكتمال

هذه مرحلة تقارير قابلة للمراجعة والاختبار، وليست شهادة اكتمال ERP بنسبة 100% أو اعتمادًا ضريبيًا. لم تُضف في هذا التغيير قوائم تدفق نقدي أو مركز مالي أو إقفال سنوي أو تسويات بنكية أو مرتجعات أو ضرائب دولة محددة. ولم تتفعّل خدمات OCR وWhatsApp وModern Soft أو تطبيقات الأجهزة الأصلية.

اعتماد نظام إنتاجي يتطلب قبول السياسات ودليل الحسابات والأرصدة الافتتاحية والضرائب والمرتجعات والتسويات والإقفال والنسخ الاحتياطي واستعادته، ثم اختبار بيئة Supabase وأجهزة الفريق والطابعات والتزامن الخادمي. التفاصيل والنتائج في `TEST_REPORT.md`.

مراجع: [دوال Supabase وصلاحيات تنفيذها](https://supabase.com/docs/guides/database/functions)، [RLS والعروض](https://supabase.com/docs/guides/database/postgres/row-level-security)، [PostgreSQL CREATE VIEW](https://www.postgresql.org/docs/current/sql-createview.html).
