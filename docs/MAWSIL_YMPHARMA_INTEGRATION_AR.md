# دمج موصل في YmPharma

## النطاق والمصدر

التنفيذ على الفرع المحلي `integration/mawsil-ympharma` المبني على
`delivery/readiness-and-ledger`، أساس `ab057872f9af65a236fdebe6243d199a5b4493bf`.
واجهة الموظفين هي YmPharma. أُعيد استخدام فكرة تخطيط الطلب من موصل وSDK الموجود،
مع ربطها بعقود `ym_api` الخاصة بالتطبيق. لم تُدمج جداول تجار موصل أو محركه المالي
المختلف في الدقة النقدية. دمج الواجهة لا يغير الجداول، لكن الاختبار على PostgreSQL
كشف عيبًا سابقًا في فحص القيود المؤجل؛ أُضيف له ترحيل أمامي مستقل موضح أدناه.

## ما يفعله الموظف

يظهر «مساعد موصل» في التنقل. يدخل الموظف طلب بيع أو بحث مخزون أو فتح تقارير.
تظهر مسودة البيع مع مطابقات من دليل المنشأة والمستودع الحاليين. يختار الموظف
العبوة صراحة، ويراجع الكمية وطريقة الدفع، ثم يفتح المسودة داخل نقطة البيع الحالية.
زر «تسجيل البيع» وحده يرسل العملية المالية؛ يحدد الخادم السعر ويتحقق من الرصيد
والصلاحيات والفترة المحاسبية. الطلبات الأخرى تفتح شاشات المخزون والتقارير الفعلية.

لا يقدّم هذا الإصدار وصفات أو نصائح طبية أو بدائل أدوية. الأدوية المقيدة أو التي
تحتاج وصفة غير قابلة للإضافة من المسودة. الديون والتحصيل والإلغاء والصوت وWhatsApp
ومزامنة Modern Soft ليست وظائف مضافة بهذا التغيير.

## حدود الأمان والبيانات

- استُبدل الرمز المشترك القديم بتحقق Supabase Auth من JWT الموظف، ثم تحقق العضوية
  والمستودع من `workspace_context`. يستخدم الخادم مفتاحًا عامًا ورمز المستخدم؛ لا service role.
- تعاد قراءة الصلاحيات بعد انتظار النموذج. لا يستطيع الكاشير فتح التقارير ولا أمين
  المخزون إنشاء مسودة بيع. الخادم يتحقق من تلك الصلاحيات، وليس إخفاء الزر فقط.
- النموذج بلا أدوات تنفيذ أو اتصال بقاعدة البيانات. مخرجاته مخطط مقيد، لا SQL أو أسعار
  أو معرفات أصناف. الاستجابة تحمل دائمًا `execution=not_executed` و`requiresApproval=true`.
- حجم HTTP حتى 16 KiB، النص حتى 2000 حرف، حتى 10 بنود، 5 ثوان لقراءة الجسم،
  40 ثانية للعمل بعد القراءة. الجلسة مرتبطة بالحساب والمنشأة والمستودع؛ تغير السياق يلغي العرض القديم.
- يوجد حد طلبين متزامنين، 6 طلبات للمستخدم و20 للجميع في الدقيقة **لكل عملية خادم**.
  هذا ليس حد إنفاق موزعًا. عند تعدد العمال أو النسخ يلزم حد مشترك في بوابة التشغيل
  وضبط الميزانية في مشروع OpenAI قبل التفعيل.
- يرسل إلى OpenAI نص الموظف فقط، دون JWT أو أسعار أو أرصدة أو كتالوج المنشأة.
  واجهة الإدخال تنبه إلى عدم إدخال بيانات المرضى. `store=false` والتتبع معطلان؛
  هذا لا يساوي ضمان انعدام الاحتفاظ لدى المزود ولا يمنع الموظف تقنيًا من كتابة بيانات شخصية.
- أخطاء SDK لا تطبع في السجلات ولا تعاد للمتصفح. رموز الجلسة لا تحفظ في تخزين المسودة.
- رُبطت طلبات البيع والشراء العادية أيضًا بهوية منشئ العملية. يفشل طلب قديم بعد تبديل
  المستخدم، مع تثبيت JWT على طلب RPC والسماح بتجديد الرمز للحساب نفسه.

## التفعيل والتحقق

المساعد مغلق افتراضيًا (`YMPHARMA_AI_ENABLED=false`). يلزم مفتاح OpenAI خادمي محفوظ
عبر المسار الآمن، واتصال Supabase ببيئة تحقق مطابقة لمخطط التطبيق، ثم تفعيل المفتاح
الوظيفي وإعادة تشغيل الخادم. لا تستخدم الرمز القديم `MAWSIL_AI_INTERNAL_TOKEN`.

لم يُنشأ مفتاح OpenAI في هذه المهمة لأن وجهة حفظه لم تُعتمد. لذلك لا يوجد إثبات لطلب
نموذج حي أو لجودة فهم العربية الحية. لا يجوز اعتبار الاختبارات البديلة إثباتًا لذلك.
يلزم قبل التشغيل الفعلي اختبار طلب عربي واضح وآخر غامض، مطابقة عبوات متشابهة،
تبديل الحساب والمستودع أثناء الانتظار، رفض صلاحيات الكاشير، مراجعة مسودة، ثم بيع واحد
على بيانات تدريب والتأكد من الفاتورة والقيد، وتكرار المرجع دون تكرار البيع.

أوامر التحقق المحلية:

```sh
npm test
npm run typecheck
npm run lint
npm run build
npm run test:db
npm run test:local-tools
```

اختبارات الواجهة تستخدم نقلًا وبيانات اصطناعية. اختُبر SQL بالمخطط الحقيقي في PGlite
وفي PostgreSQL 16 داخل حاوية مؤقتة، بما فيه سباقات جلسات مستقلة. لا تثبت هذه
الاختبارات اتصال قاعدة الموظفين الحالية. تقرير النتائج النهائي في نهاية هذا المستند.

## إصلاح إغلاق المعاملة المالية

فشل 45 اختبارًا من 68 على PostgreSQL قبل الإصلاح برسالة
`UNBALANCED_OR_UNPOSTED_JOURNAL`، رغم نجاح المحاكي سابقًا. الفحص المؤجل
`ym_private.balance_check` كان `SECURITY INVOKER`: عند COMMIT بعد عودة RPC
المميّز يعمل بصلاحيات مستخدم لا تسمح له RLS برؤية القيود. النتيجة رفض شراء أو بيع صحيح.

الترحيل `20261008013715_ympharma_deferred_balance_guard.sql` يعالج **دالة trigger
خاصة فقط** لتفحص الحالة النهائية الكاملة للقيد بصلاحيات المالك، مع `search_path` فارغ،
وفشل صريح عند غياب القيد، وسحب التنفيذ المباشر من PUBLIC وanon وauthenticated
وservice_role. لا تُمنح قراءة القيود للكاشير ولا صلاحيات كتابة إضافية. لا تعتمد الدالة
على معرف قيد من طلب HTTP؛ تستعمل الصف المسبب للـtrigger. اختُبر قبول القيد الصحيح
ورفض غير المتوازن عند COMMIT ككاشير، وبقاء RLS وحجب الكلفة والعزل بين المنشآت.

الترحيل أُضيف إلى مخطط YmPharma في `sprints/01-database/supabase/migrations`،
ولم يُطبّق على الإنتاج أو على مخطط موصل التاريخي في جذر المستودع. يجب مقارنة نسخة
قاعدة الهدف وترحيلاتها قبل تطبيق هذا الملف وحده على بيئة قائمة؛ لا تعاد ترحيلات baseline
فوق قاعدة حقيقية. أُضيف أيضًا حد اتصال لاختبارات PostgreSQL كي يفشل الاتصال المتعطل
بدل تعليق الاختبارات بلا نهاية.

## إصلاح الحزمة المستوردة

حزمة `../financial-patch` مستقلة عن هذا التطبيق. أُصلح فيها انتقال هوية صاحب طابور
البيع عند تبديل الحساب: تثبيت هوية نصية قبل قراءة الصفحة، والتحقق قبل الحفظ والإرسال
وكل إعادة محاولة. لا تُستورد هذه الحزمة أو ترحيلاتها إلى YmPharma تلقائيًا.
الاختبار الجديد `tests/actor-binding.test.mjs` أعاد إنتاج المشكلة قبل الإصلاح،
وأصبح يرفض التبديل، بما فيه تغيير كائن الجلسة نفسه، ويقبل تجديد الرمز للمستخدم نفسه.

## التراجع

تعطيل `YMPHARMA_AI_ENABLED` وإعادة التشغيل يغلق نقطة المساعد دون المساس بوظائف
نقطة البيع والتقارير. لم تتغير الجداول أو السجلات المالية أو عقود RPC. لا تُعد دالة
فحص القيد إلى النسخة القديمة لإلغاء المساعد؛ إصلاح رفض القيود الصحيحة مستقل عنه.
التراجع عن الواجهة يتم بمراجعة الفرع دون حذف بيانات.
